# pet925 プロジェクト・サマリー

## 🏆 到達レベル
**大規模データ・アーキテクチャを設計・運用できる「シニア級エンジニア」**
単なるWebサイト制作に留まらず、10万件規模のデータをブラウザ上で快適に処理するためのマルチスレッド化（Web Worker）や、Pythonによる厳格なデータビルドパイプラインを構築できるレベルに到達しています。
具体的には、**10万件の商品データに対して、検索・フィルタリング処理を200ms以内に完了させ、UIスレッドをブロックしない（フリーズさせない）**ことを目標としています。

## 🛠 習得・活用した技術
1. **データ駆動型アーキテクチャ (Data-Driven)**
   - 人間が編集する「マスターデータ(.ods)」と、プログラム用の「中間データ(.csv)」、Web用の「配信データ(.js)」を分離するプロの設計思想。
   - 商品データ本体をJSONファイルとして分離し、必要な時に非同期で取得するモダンな設計。
2. **ビルドオートメーション (Python)**
   - Pythonを用いた高速なデータ変換・バリデーションスクリプト (`csv_to_json.py`)。
   - 複数CSVの統合、自動タグ付け、ブランド名寄せ、重複チェック、カテゴリ順ソートの自動化。
3. **超大規模データ向けパフォーマンス最適化**
   - **Web Worker によるマルチスレッド処理**: 検索処理をメインスレッドから分離し、10万件のループを回しても画面が一切固まらない（フリーズしない）UI体験を実現。
   - **IndexedDB による永続化キャッシュ**: 処理済みの商品データをブラウザ内に保存。2回目以降のアクセスではサーバー通信をスキップし、パース済みのデータを即座に展開。
   - **検索用インデックスの事前生成**: 正規化済みの結合文字列（`_searchFullText`）をメモリ上に構築し、キーワード検索を高速化。
   - **Incremental Loading**: DOM生成を最小限（30件ずつ）に抑えるページネーション設計。
   - **ステートベースのUI切り替え**: 検索条件設定と結果一覧を別Viewとして定義し、`body`クラス（`state-results`）で一括制御するプロフェッショナルな画面遷移ロジック。
   - **CSSアニメーション最適化**: `cubic-bezier` を用いた滑らかなヘッダーの伸縮と、`fadeInUp` アニメーションによるリスト登場の演出。
4. **厳格なデータバリデーション (QA)**
   - 正規表現（Regex）を駆使した高度な CSV パース処理。
   - 未登録タグ、未登録ブランド、商品名重複、必須項目欠落をビルド時に自動検知。
   - エラー発生時にデプロイを強制停止するガードレール機能 (`sys.exit(1)`)。
5. **モダン・フロントエンド**
   - Vanilla JS によるデータ駆動の UI 生成。
   - **CLS (Cumulative Layout Shift) 対策**: 複数選択ボタンの幅を固定し、チェックマークを絶対配置することで操作時のガタつきを解消。
   - CSS Grid/Flexbox や Backdrop-filter を使ったカタログ風デザイン。
   - **表示パフォーマンス最適化**: `loading="lazy"` や `decoding="async"` の導入。
   - **堅牢なプレースホルダー**: Data URI (SVG) を使った、外部リクエスト不要の「No Image」表示ロジック。

## � トラブルシューティングと学びの記録

### 1. ディレクトリ構造の最適化とパスの管理
- **経過**: `public/` フォルダを廃止し、`index.html` と `data.js` をルートへ移動してデプロイを簡略化。
- **学び**: Node.js の `__dirname` と `path.join` を使った相対パス指定の重要性。フォルダ構成変更時にスクリプト内の出力先パスを同期させないと `ENOENT` エラーが発生することを実体験として理解。

### 2. 関数設計とスコープの理解 (`ReferenceError`)
- **経過**: `useHeaderMap is not defined` エラーを、関数の引数設計を見直すことで解決。
- **学び**: 関数に引数を追加した際、呼び出し側と定義側の整合性を保つ重要性。また、デフォルト引数 `(content, useHeaderMap = true)` を活用することで、既存コードを壊さずに機能を拡張する手法を習得。

### 3. CI環境 (GitHub Actions) への対応
- **経過**: GitHub Actions 上でエラーが発生した際、何が原因か GitHub の画面上ですぐに分かるように「日本語のヒント」と「Workflow Commands」を導入。
- **学び**: 実行環境（`process.env.GITHUB_ACTIONS`）を検知して挙動を変える手法や、エラー時に終了コード `1` を返して安全にパイプラインを止める「壊さない開発」の考え方を習得。

### 4. 汎用的な関数によるコードの共通化 (DRY原則)
- **経過**: `tags.csv` や `brands.csv` の読み込み処理を `loadSettingsCSV` 関数に統合。
- **学び**: 重複する処理を一つにまとめることで、バグを減らしメンテナンス性を高める「プロの設計」を実践。

### 5. ブラウザのキャッシュ管理
- **経過**: コード修正が画面に反映されない現象への対処。
- **学び**: Web開発特有の挙動であるブラウザキャッシュへの理解。開発中の **Ctrl + F5**（強力な再読み込み）の習慣化。

### 6. Google Analytics (GA4) 高度な計測と分析
- **経過**: GA4の計測がローカルで動かず、本番環境でも検出されない問題に直面。
- **学び**:
    - `index.html` でのURL同期 (`updateURL`) により、SPA（シングルページアプリケーション）形式のサイトでもGA4の `page_view` イベントを正確に計測する手法。
    - **サイト内検索の可視化**: `gtag('event', 'search', ...)` を実装し、ユーザーが実際に入力したワードをGA4で分析可能に。
    - **欠落需要の発見**: 検索結果が0件だった際に `search_no_results` イベントを送信し、品揃え改善に繋げる手法。
    - `event_category`, `event_label` をカスタムディメンションとして登録し、アフィリエイトクリックやフィルタ選択を詳細に分析する手法。
    - ローカル開発環境 (`file:///`) でのGA4計測の課題 (`cookie_domain: 'none'`) と `Live Server` の活用。
    - `debug_mode: true` を用いた `DebugView` でのリアルタイム検証の重要性。
    - `favicon.ico` の404エラーは計測に影響しないことの理解。
    - ブラウザの広告ブロックやトラッキング防止機能がGA4計測を阻害するケースとその対処法。

### 7. Git運用とデプロイの効率化
- **経過**: `data.js` の更新忘れやGit競合により、デプロイが停止する問題が発生。
- **学び**:
- **一気通貫のデプロイ**: `python3 csv_to_json.py` による検品・ビルドを起点に、Git push までを自動化。
- VS Codeの自動貼り付け（Apply）が失敗する原因（コードのズレ）と手動対処法。

### 8. パーソナライズ機能（お気に入り）の実装
- **経過**: ユーザーが気になるフードを保存できる「お気に入り」機能を導入。
- **学び**: 
    - `localStorage` を用いた永続的なデータ保持。
    - 検索結果画面内でリアルタイムに件数をカウントし、トグルボタンに反映させる動的なUI制御。
    - 標準の `confirm()` ダイアログを廃止し、サイトのデザインに合わせたカスタムモーダルを実装することで、ブランドの世界観を崩さないUXを提供。

### 9. セキュリティとパフォーマンスのトレードオフ
- **経過**: パクリ防止のために一度 Base64 による難読化を導入したが、ファイルサイズが約 33% 増加したため、読み込み速度を優先して廃止。
- **学び**: 
    - セキュリティ対策が通信量やパース時間に与える影響の定量的理解。
    - 「100%の防御」よりも「ユーザーの快適さ（UX）」を優先し、パクリ防止はコンソール警告や著作権表示といった「ソフトな抑止力」に留めるというシニア級の意思決定。

### 10. 高度なキャッシュバスティング
- **経過**: `data_master.js` 自体がキャッシュされると、後続の `siteVersion` が更新されない問題を解決。
- **学び**: 
    - `document.write` を用いて、入り口となるマスタースクリプトに `Date.now()` でタイムスタンプを付与して動的に読み込む手法。
    - これにより「データ更新時のみ巨大なJSONを再ダウンロードさせ、それ以外はキャッシュを利用する」という理想的なブラウザ制御を実現。

### 11. ターゲットを絞ったUIデザインの洗練
- **経過**: お気に入りボタンのデザインを「控えめだが高品質」なスタイルへ。
- **学び**: 
    - 全体をピンクにするのではなく、アイコンだけをピンクにする「引き算のデザイン」。
    - ホバー時の浮き上がりや、クリック時の凹みといった「マイクロインタラクション」による操作感の向上。

### 12. UI/UX の微細なこだわりとアクセシビリティ
- **経過**: 「こだわり」タグを選択した際にボタンが動く問題を修正。また、ラベルを「こだわり・お悩み」に変更。
- **修正**: フィルターカテゴリおよび商品カード内タグの表示順を「種類 (Animal) → 年齢 (Age)」に完全固定。カテゴリ名の大文字小文字の揺れも吸収。
- **UI整理**: 商品カード内の基本タグ（種類・年齢）を非表示化。冗長な情報を削ぎ落とし、「こだわり・お悩み」タグのみを際立たせるミニマルな設計へ。
- **注釈の削除**: グレインフリー商品に表示されていた「※この商品はグレインフリーです」という冗長な注釈テキストを削除。
- **テキスト表示の最適化**: 商品名のフォントサイズを微調整（1.15rem -> 1.05rem）し、最大表示行数を3行に拡張。長名称の商品でも情報が途切れにくい設計に改善。
- **レイアウトの最適化**: コンテンツ量に関わらずボタン位置やテキスト領域が揃う「垂直カード・グリッドレイアウト」を最終採用。ガタつきのない安定した視認性を確保。
- **追加**: サイトコンセプトを説明する導入文をヘッダーに追加。
- **微調整**: 導入文を「ー愛犬・愛猫にぴったりのフードを探せるお手伝いをー」へ変更。より親しみやすく、かつ極限までシンプルに整理。
- **学び**: 
    - ユーザーが操作した瞬間にレイアウトが崩れる不快感を取り除く重要性。
    - 文言ひとつでユーザーが「自分に向けられたサイトだ」と感じる心理的効果（こだわり -> こだわり・お悩み）。
    - 初見のユーザーに対して、サイトの価値（何ができるか）を言語化して提示することの信頼性向上効果。

### 13. 画像の最適化と信頼性
- **経過**: 画像未設定時のプレースホルダーが表示されない問題を、Data URI SVG を使って解決。
- **学び**: 外部リソース（Unsplash等）に依存しすぎず、自律的に動くコードを書く重要性。

### 14. データの「名寄せ」と検索ロジックの進化
- **経過**: `brands.csv` に登録がある場合、入力が多少揺れていても正式名称に自動変換するロジックを `convert.js` に追加。
- **ロジックの共通化**: `index.html` と `search_worker.js` の正規化（normalize）ロジックを統一。
- **ブランドID方式**: ブランド名をアルファベットのまま維持しつつ、裏側で日本語名も検索対象に含める `brand_id` リンク方式の確立。また、内容量（`size`）も検索用インデックスに含めることで、表示せずとも「2kg」などのワードで絞り込みが可能。

### 15. ブラウザキャッシュと Worker の生存管理
- **トラブル**: コードを更新しても検索結果に反映されない。
- **解決策**: Web Worker の読み込みURLにタイムスタンプを付与（`?v=Date.now()`）し、キャッシュを強制破棄するキャッシュバスター手法を導入。

### 16. 大規模データ（10万件）へのスケーラビリティ対応
- **経過**: 商品数が数千〜1万件に増えることを見据え、初期描画を30件に制限し「さらに表示」ボタンで拡張するロジックを導入。
- **汎用的な拡張性**: フード以外（用品・おもちゃ等）の追加を見据え、`type` カテゴリによる動的フィルタリング基盤を構築。
- **UIのスケーラビリティ最適化**: カテゴリー増大に対応するため、「アクティブ・フィルター・チップス」「カテゴリー別アコーディオン」「一括クリア機能」を実装。情報密度と操作性を両立。
- **1万件規模への対応（パフォーマンス最適化）**: 大規模データ時のブラウザ負荷を抑えるため、「Incremental Loading（もっと見る）」機能を実装。必要な分だけDOMを生成するプロのフロントエンド設計を導入。
- **価格比較の準備**: 3モールの価格データを数値型（`Number`）として保持。将来の「安い順ソート」や価格表示の導入に向けたデータ基盤を構築済み。

### 17. データフォーマットの最適化（JSON vs JS）
- **学び**: 巨大なデータをJavaScriptコードとして読み込むよりも、JSONとして読み込み `JSON.parse()` する方が、ブラウザのパース速度とメモリ効率が圧倒的に優れていることを実証。

### 18. 戦略的「非表示」設計とデータの蓄積
- **学び**: リリース初期はUIをシンプルに保つため、サイズや価格をあえて非表示に。しかし、データとしてはビルドパイプラインで正規化し蓄積し続けることで、将来の機能拡張時にシステム変更を最小限に抑える「データ資産」の考え方を実践。

### 19. モード切り替え型 UI (Search vs. Results) の導入
- **経過**: 検索条件の選択肢が増えたため、条件設定と結果表示を切り替える方式を採用。
- **学び**: 
    - 実行ボタン（「◯◯件を表示」）をフローティング配置し、ユーザーに期待感を持たせるUI。
    - 検索実行時にヘッダーをスッと畳んで固定（Sticky）し、検索窓をヘッダーに吸い込ませることで、コンテンツ領域を最大化する設計。

### 20. ユーザー体験を損なわないスムーズな状態遷移
- **経過**: 画面切り替え時に `window.scrollTo` を組み合わせ、ユーザーが迷子にならないように調整。
- **学び**: Viewを切り替えるだけでなく、視点の位置（スクロール位置）を制御することが、シングルページでのUX向上に不可欠であるという知見。

### 21. フロントエンドのモジュール分割と読み込み順序の制御
- **経過**: HTMLファイルが肥大化したため、CSSとJSを外部ファイル化。その際、動的なスクリプト読み込みによる `ReferenceError` が発生した。
- **学び**: `document.write` を用いて同期的に読み込む順序を固定し、キャッシュバスティング（`siteVersion`）を維持したまま実行タイミングの齟齬を解消。大規模開発における資産管理（Asset Management）の重要性を再認識。

### 22. 多層防御によるサイトコピー対策
- **経過**: 静的サイトの宿命であるコンテンツコピー（ミラーサイト）に対する懸念。
- **学び**: `authorizedDomains` によるドメインロック（技術的抑止）と `canonical` タグ（SEO/構造的抑止）を組み合わせ、さらにコンソール警告（心理的抑止）を重ねることで、100%の防御は不可能でも、疑似サイトの有用性を著しく低下させる「実利的な防衛策」を習得。

### 23. AI自動収集パイプラインの堅牢化
- **経過**: AIが生成するデータに余計なヘッダーや解説が混じることで発生するパースエラー。
- **学び**: プログラム側で「お掃除（ヘッダー除去・バリデーション）」を徹底し、AIが多少不安定でもシステム全体として正しく動く「疎結合な自動化」を構築。

### 24. アフィリエイト・エコシステムの統合と収益化効率化
- **経過**: Amazon/楽天/Yahoo!の各社IDを個別に管理する手間と振込手数料のロスを解消するため、「もしもアフィリエイト」経由の統合検索リンク生成ロジックを実装。
- **学び**: ゲートウェイURLで検索結果をラップする手法により、メンテナンス性を損なわずに全ての動線を収益化する実利的な設計。

### 25. 法的コンプライアンスとステマ規制（PR表記）への対応
- **経過**: 公開にあたり、Amazonアソシエイト規約の遵守（特定文言の掲載）および景品表示法（ステマ規制）への対応として、プライバシーポリシー・免責事項のモーダルを実装。
- **学び**: 技術だけでなく、運営者としての法的責任（免責事項）やプラットフォーム規約を「コードとドキュメント」の両面で担保するプロ意識。

### 26. 開発体験（DX）の向上：高速エクスポートマクロ
- **経過**: Linux環境でのLibreOffice Calcの重さを解消するため、全シートではなく「現在のシートのみ」を瞬時に書き出す高速マクロを導入。

### 27. アナリティクス送信の完全デバウンス化
- **経過**: 入力中の文字ごとにGA4イベントやWorkerが動く負荷を抑えるため、検索ロジックと計測イベントを800msのデバウンス処理へ完全統合。
- **学び**: UIの反応速度とシステム負荷のトレードオフを考慮し、タイピング停止時のみ重い処理を走らせる「シニア級」のフロントエンド設計を確立。

### 28. フィルターUIの論理的構造化
- **経過**: タグの表示順がデータの出現順に依存していた「不揃いさ」を解消するため、`CATEGORY_PRIORITY` による順序固定ロジックを導入。

- **戦略的判断**: サイト初期段階での過度なアフィリエイトリンク設置は、プラットフォーム審査（楽天・Amazon等）における「コンテンツ不足」による却下リスクを高めると判断。

### 58. 楽天Product Search API(v2) による高画質カタログ画像の自動取得
- **経過**: Yahoo!ショッピングAPIから取得した画像はショップロゴ・透かし（サブ文字）が入った低品質なものであった。また、従来の楽天商品価格ナビAPIの呼び出しが古いエンドポイント（`app.rakuten.co.jp`）を参照しており、別途 `RAKUTEN_APP_ID` が必要と判断されてスキップされていたため、結果的にYahoo画像しか使われていなかった。
- **解決策**: 同じApp IDで利用可能なマイクロサービス版 Product Search API（`ichibaproduct/api/Product/Search/20250801`）を発見。`fetch_rakuten_product_data_v2()` 関数を新設し、画像取得の最優先として設定。加えて画像スコアリングのGoodパターンに `r.r10s.jp` を追加。
- **成果**: 全20件中19件のJANコード商品が楽天公式カタログ画像（透かし・ロゴなし、`?_ex=...`除去済みの高画質約40KB）に置き換わった。残り1件は従来のYahoo→IchibaItem→推測の順でフォールバックされる。
- **UI改善**: 画像左上の「参考画像」バッジと画像下の「出典: ...」注釈を削除。楽天公式カタログ画像であるため不要と判断。
- **学び**: 同じAPIキーでもエンドポイント（`ichibams` vs `ichibaproduct`）が異なると提供されるデータ品質が大きく異なる。マイクロサービスアーキテクチャの特性を理解し、目的に応じた最適なエンドポイントを選択する重要性を再認識。

### 59. 楽天公式カタログ画像の法的安全性
- **経過**: Yahoo!ショッピングAPIからの画像（ショップロゴ・透かし入り）に代わり、楽天Product Search APIから取得したカタログ画像（`r.r10s.jp`）を使用することの法的リスクを評価。
- **判断根拠**:
  1. **楽天API利用規約の範囲内**: 楽天が公式に提供するAPI（Product Search API）を経由して取得した画像であり、利用規約に基づく適法な利用。
  2. **商品紹介目的の引用**: 商品画像は商品紹介（引用）の範囲内で使用しており、出典元（楽天市場）へのリンクを各商品カードに併記している。
  3. **直リンク方式**: 自サーバーへの複製・再配信ではなく、楽天のCDNからの直リンクを採用。著作権者の配信管理権を尊重。
  4. **ショップロゴ・透かしの不在**: Yahoo画像に見られた「Powerd by Yahoo!」等の透かしがない、純粋な商品パッケージ画像。
- **結論**: 商用サイトとしても実務上許容される範囲内であり、静的サイトとしての健全性を維持している。
- **学び**: 画像の品質向上と法的リスク低減はトレードオフではなく、適切なAPIエンドポイントを選択することで両立可能であることを実証。

### 60. JANコード自動収集パイプラインの整理とドキュメント統合
- **経過**: `jan_data_collector.py`（画像・商品名・リンクのみを取得する簡易版）と `auto_collect_all.py`（説明文自動生成・タグ判定まで行う上位互換版）という2つのJANコード収集スクリプトが存在していたが、運用手順やデータの扱われ方（追加か上書きか）が明文化されていなかった。

- **対応内容**:
    - `index.html` の `mailto:` リンクから実アドレスを削除し、`id="contact-mail-link"` を付けた空リンク（`href="#"`）に変更。
    - `csv_to_json.py` に `load_contact_config()` を追加し、既存の `RAKUTEN_APP_ID` 等と同じパターンで `.env` の `CONTACT_EMAIL` を読み込み。ビルド時（`data_master.js` 生成時）に、アドレスを平文ではなく文字コード配列 `CONTACT_MAIL_CODES`（`[ord(c) for c in CONTACT_EMAIL]`）として書き出すよう変更。

    - `.env` に `CONTACT_EMAIL=your-email@example.com`（プレースホルダー）を追加。実運用時はこの1行を実アドレスに書き換えて `npm run build` を実行するだけで反映される。
- **学び**:
    - `.env` は「サーバー/ビルド環境だけで完結し、ブラウザに配信されるファイルには一切含まれない秘密情報」の置き場所であり、最終的にクライアント側JSに含める必要がある値（メールアドレス等）を隠す用途には本質的に使えないという性質の違いを明確化。

### 69. `normalize()` 正規化ロジックの共通化（`common.js` の新設）
- **経過**: 検索キーワードの正規化ロジック（全角半角・ひらがなカタカナの揺れを吸収する `normalize()`）が `main.js`（メインスレッド）と `search_worker.js`（Webワーカー）の両方に全く同じ内容でコピーされており、片方だけ修正して挙動がズレる事故のリスクがあった。
- **対応内容**: `normalize()` のみを `common.js` に切り出し、`index.html` からは通常の `<script>` タグで、`search_worker.js` からは `importScripts()` で、同じファイルを読み込むように変更。ES Modules は使わず、既存の「グローバル関数を素の `<script>`/`importScripts` で共有する」方式をそのまま踏襲したため、読み込み順序（`common.js` → `main.js`）とキャッシュバスティング（`?v=siteVersion`）の仕組みは変更なし。
- **学び**: Web Worker は別スレッドでモジュール共有に制約があるが、ES Modules化せずとも「共通ロジックだけを1ファイルに切り出し、両方から読み込む」という単純な方法で重複コードの修正漏れリスクを解消できる。大がかりなアーキテクチャ変更を伴わない、コストの低いリファクタリングの好例。

### 70. 検索ボックスの自由入力語に反応する「キーワードコメント」機能の追加
- **経過**: 検索結果画面の店員コメント（`pickStoreComments()`）は、選択中の `cond`/`animal` タグにしか反応せず、フィルターに存在しない話題（例:「心臓」「納豆菌」など特定の症状・成分に関するフリーワード）には一切反応できなかった。一方で、これらの話題をいちいち `tags.csv` の正式なタグとして追加すると、フィルターUIの肥大化や `rules.csv` 経由の商品自動タグ付けへの意図しない副作用（無関係な商品への誤タグ付与）を招くリスクがあった。
- **対応内容**:
    - 新しいCSVファイルは作らず、既存の `comments.csv` に新しい `category: keyword` を追加する形で対応。`csv_to_json.py` は products/categories/tags/rules 以外のCSVを無検証で汎用マスターとして読み込む仕組み（`SPECIFIC_MASTER_CSVS` に含まれないCSVの自動取得処理）に元々乗っているだけなので、Pythonビルド側は無改修で対応できることを確認済み。
    - `main.js` に `pickKeywordComments(searchVal)` を新設。検索ボックスの入力文字列を `normalize()` した上で、`comments` 配列から `category === 'keyword'` の行の `key` と部分一致するものを検索し、最大1件をランダムに返す。既存の `pickStoreComments()`（タグ選択由来）は無改造。
    - `renderResultComment()` で両者の結果を合算する際は「フィルター由来コメント（最大2件）はそのまま、キーワード一致があれば常に追加でもう1件」という**追加スロット方式**を採用。既存の見え方・優先順位ロジックを一切変更せず、フリーワードへの反応を純粋な"上乗せ"として実装した。
    - 動作確認用に `comments.csv` へ `keyword,心臓,...` / `keyword,納豆菌,...` のサンプル行を追加し、`csv_to_json.py` のビルドがエラーなく通ること、および正規化・部分一致ロジックがNode.js上で期待通り動作すること（完全一致／文中埋め込み／無関係語で反応しない、の3パターン）を確認した。
    - `docs/MANUAL.md` の「9. コメントの追加（comments.csv）」が実態と異なる古い列構成（`product_id`/`author`）を記載していたため、実際の列構成（`category`/`key`/`comment`）と `keyword` カテゴリの使い方に合わせて修正した。
- **学び**: 新しい要件が出たときに「まず新しいファイル・新しいタグを作る」のではなく、既存のデータ構造（今回は無検証で汎用的に読み込まれる `comments.csv`）を拡張できないか検討することで、ビルドパイプラインへの変更ゼロで機能追加できるケースがある。また、「既存機能を変えずに追加する」（フォールバックではなく常時追加スロット）という組み合わせ方針は、実装の見通しの良さと既存動作の安全性を両立させる選択として有効だった。

### 71. JSDoc + `jsconfig.json` による型チェックの導入と、Jestユニットテストの追加
- **経過**: フレームワーク（React等）やビルドツールの導入は「配信ファイルが重くなる」ため避けたいが、テスト・型安全性の欠如（`package.json`に`"test": "jest"`はあるが実体のテストファイルが皆無、型注釈も一切なし）は改善したいという要望があった。前者（配信ファイルの重さ）と後者（開発時の品質担保）は本来トレードオフではなく、テスト用ツール（Jest）やJSDoc型チェックはいずれも**開発時・エディタ上でのみ動作し、ビルド後の配信ファイルには一切含まれない**ため、両立可能であることを確認した上で着手した。
- **対応内容**:
    - `common.js` と、新設した `comment_logic.js`（下記#72）に `// @ts-check` プラグマとJSDocコメントを追加し、`jsconfig.json`（`checkJs: true`、DOMライブラリ込み）でエディタ上の型チェックを有効化。`data_master.js`（ビルド生成物）も`include`に加えることで、`tagMaster`/`comments`等のグローバル変数がTypeScriptの「グローバルスクリプトのスコープ統合」機能により自動的に型解決されることを確認（別途アンビエント型定義ファイルを書く必要がなかった）。
    - `search_worker.js` はWebWorkerグローバルスコープ（`self`）で動作するため、DOMライブラリと共存させると型定義が競合しやすく、`jsconfig.json`の対象からは除外。JSDocコメントによる可読性向上のみ行い、型チェックの強制はしないという判断をコメントで明記した。
    - `main.js` は既存コードの規模・DOM依存の多さ（`getElementById(...).value`のnullチェック省略など）を踏まえ、`// @ts-check`の強制は見送り、主要な純粋関数（`getSearchUrl` / `tryNextImageSource` / `getProductImageSrc` / `toggleFavorite` / `getMoshimoUrl`等）にJSDocのみ追加する現実的な範囲に留めた。
    - `package.json` に `devDependencies: { "jest": "^30.3.0" }` を追加（既に`node_modules`にはインストール済みだったが`package.json`未記載だったため、`npm install`での再現性を確保）。TypeScript本体はインストールしていない（`// @ts-check`はエディタ内蔵のTypeScript言語サーバーで動作するため、プロジェクトの依存関係としては不要）。
    - `tests/common.test.js`（`normalize()`の正規化パターン）、`tests/comment_logic.test.js`（`getCommentLookup()` / `pickStoreComments()` / `pickKeywordComments()`）を新設。計19件のテストケースが `npm test`（Jest）で全て通ることを確認。
- **学び**: 「重さ」の議論をする際は、「ブラウザに配信されるもの」と「開発者のマシン上だけで完結するもの」を明確に切り分けることが重要。フレームワーク導入への慎重さと、テスト・型安全性への投資は対立しない。また、TypeScriptの`checkJs`はグローバルスクリプト（`<script>`タグで読み込む、`import`/`export`を使わないファイル）同士のスコープを自動的に統合してくれるため、レガシーな「グローバル変数共有」スタイルのコードベースでも、アンビエント型定義を大量に書かずに型チェックを導入できるケースがある。

### 72. 店員コメント選定ロジックの`comment_logic.js`への分離（テスト容易化のためのモジュール分割）
- **経過**: #71でJestテストを書く際、`pickStoreComments()` / `pickKeywordComments()`が`main.js`内に定義されていたため、これらをテストするには`main.js`全体を`require`する必要があり、ファイル末尾の自己実行コード（`initializeApp()`の自動呼び出し、`new Worker(...)`の生成等）が副作用として発生してしまい、Jest（Node環境）では正しく動かない・不必要な複雑さを生む問題があった。
- **対応内容**: 店員コメントの選定に関わるロジック（`getCommentLookup` / `commentLookupMap` / `STAFF_ICON_IMAGES` / `MAX_STORE_COMMENTS` / `pickStoreComments` / `pickKeywordComments`）を`main.js`から`comment_logic.js`という新しいファイルに丸ごと移動。ブラウザでは`index.html`から`common.js`の直後・`main.js`の直前に読み込むことで、グローバル関数として今まで通り`main.js`から呼び出せるようにした（呼び出し側のコードは無変更）。テスト時に`activeFilters`/`comments`グローバルへの依存を弱めるため、`pickStoreComments(filters)`・`pickKeywordComments(searchVal, commentsData)`に「省略時はグローバル変数、指定時はそれを使う」というオプション引数を追加（既存の呼び出し方法との後方互換を保ったまま、テストからは任意のフィクスチャを直接渡せるようにした）。
- **動作確認**: Node.jsの`vm`モジュールで実際のブラウザ読み込み順（`data_master.js`→`common.js`→`comment_logic.js`）を再現し、実データ（`comments.csv`由来）で`pickStoreComments`/`pickKeywordComments`が分割前と同じ結果を返すことを確認。`python3 csv_to_json.py`のビルドと`node --check`による構文チェックも通過。
- **学び**: 「テストを書きたいのに書けない」原因の多くは、対象コードが「テストしたい純粋なロジック」と「アプリ起動時の副作用（DOM操作・通信・Worker起動）」が同じファイル・同じスコープに混在していることに起因する。両者を分離するのは大規模なアーキテクチャ変更ではなく、影響範囲を絞った小さなリファクタリングとして安全に行えることを実証した。

### 73. `jsconfig.json`の設定ミス修正（`main.js`に126件の警告が出ていた問題）
- **問題**: #71で`jsconfig.json`の`checkJs`を`true`（全体有効）にした状態で`main.js`も`include`に入れていたため、`main.js`側に`// @ts-check`を付けていないにもかかわらず、エディタ上で`main.js`全体が型チェックされてしまい、「問題」パネルに126件もの警告が出る事態になった。TypeScriptの`checkJs`は「グローバル設定を`true`にすると`include`対象全ファイルが検査される（個別ファイルの`// @ts-check`は`false`設定時のオプトイン用）」という仕様を見落としていた。
- **対応**: `jsconfig.json`の`checkJs`を`false`に変更。これにより、ファイル先頭に`// @ts-check`があるファイル（`common.js`・`comment_logic.js`）だけが個別にオプトインで型チェックされ、`main.js`・`data_master.js`は検査対象から外れる（ただし`include`には残しているため、グローバル変数の補完・定義ジャンプは引き続き機能する）。
- **学び**: JSDoc型チェックを既存の大規模ファイルに"侵食"させずに導入したい場合は、「グローバルで有効化 + 個別ファイルは`@ts-nocheck`で除外」ではなく、「グローバルで無効化 + 個別ファイルは`@ts-check`で追加」の方が安全（対象を明示的に許可リスト化できるため、新しく`include`にファイルを追加した際に意図せず検査対象が広がる事故を防げる）。
